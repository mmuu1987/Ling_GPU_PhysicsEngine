## A. 全局属性保存失败破坏撤销备份

**优先级：P2；建议第一项。**

### 代码依据

- [WarSandboxUnitStatStore.cs:95–106](../Assets/Game/Scripts/WarSandboxUnitStatStore.cs#L95-L106)：`TrySave` 先以 `Current` 覆盖 `BackupPath`，随后写主文件；主文件写入失败没有恢复旧备份。
- [撤销实现:110–117](../Assets/Game/Scripts/WarSandboxUnitStatStore.cs#L110-L117)：读取备份、写回主文件，再删除备份。
- [原子写辅助:120–139](../Assets/Game/Scripts/WarSandboxUnitStatStore.cs#L120-L139)：单个文件使用临时文件、刷盘和 `File.Replace`，但两次文件更新不是整体提交。
- 玩家入口：[兵种库保存与撤销:168–175](../Assets/Game/Scripts/WarSandboxFrontEnd.UnitLibrary.cs#L168-L175)。

### 最小复现

1. 使用独立临时目录与新的 `WarSandboxUnitStatStore`。
2. 成功保存 A，再成功保存 B；确认主文件 B、备份 A。
3. 保持备份目录可写，仅让主文件替换失败，例如使用 Windows 上不允许删除共享的文件句柄。先确认故障确实落在主文件替换阶段，不是更早的读取或序列化阶段。
4. 尝试保存 C。
5. 当前代码预期：返回 false，主文件 B，备份却变为 B；释放故障后撤销无法恢复 A。

### 影响与最小修复方向

当前有效主文件并未丢失，但上一次成功修改的撤销数据丢失。

主文件存在时，优先利用已刷盘临时文件和 `File.Replace(temp, FilePath, BackupPath)`，让备份轮换伴随主文件替换进行。此为建议方向，需核验目标 Windows/Unity 运行时的失败语义。首次保存仍须支持撤销回空全局覆盖；不能删除这一既有能力。缓存只在成功提交后更新。

### 验收

- A、B成功，C失败后主文件和原备份均保持原字节，缓存仍为 B。
- 释放故障后撤销恢复 A。
- 首次保存可撤销回官方值；正常保存、重开读取与撤销保持。
- 失败不遗留临时文件，错误信息明确。
- 复用并扩展[现有属性测试:276–298](../Assets/Game/Tests/EditMode/WarSandboxUnitStatsTests.cs#L276-L298)，不只增加成功路径用例。

## B. GPU 初始化中途异常后，半成品仍可能进入调度

**优先级：P2；若普通启动或重开已有此现象，升为 P1。**

### 代码依据

- [初始化:326–339](../Assets/MassEngine/Core/MassEngineManager.cs#L326-L339)：先记录分配签名，再 `Allocate`、`InitializeAll`、上传；缺少异常回滚。
- [分配状态:89](../Assets/MassEngine/Core/MassGpuBufferManager.cs#L89)：`IsAllocated` 仅检查首块 `agentBuffer` 非空且人数大于零。
- [每帧入口:174–202](../Assets/MassEngine/Core/MassEngineManager.cs#L174-L202)：相同签名下不重建；未检查完整初始化就绪状态，继续调度。
- [调度器:47–72](../Assets/MassEngine/Core/ComputePipelineOrchestrator.cs#L47-L72)：同样只检查 `IsAllocated`，随后绑定、派发与交换缓冲。
- [流场容量:117–119](../Assets/MassEngine/Core/MassGpuBufferManager.cs#L117-L119)：尺寸先用 `int` 相乘；[167–178](../Assets/MassEngine/Core/MassGpuBufferManager.cs#L167-L178)才转为 `long` 检查上界。

### 触发条件与影响

首块 buffer 成功后，后续分配、上传或自定义模块初始化抛异常。部分资源仍被视为可运行，下一帧可能使用缺失或未上传的资源，连续报错或错误仿真，已分配资源未及时回收。

明确边界输入是流场分辨率 `65536`：在通常未检查的整数运算下，平方溢出为零，上界检查漏过后构造零长度 buffer 抛异常。此为开发配置边界，**不表示现役默认配置已触发**。

### 最小复现与修复方向

使用少量单位、小网格和私有配置，注入可控初始化异常；不要用真实 OOM。可选择上述流场维度，或现有扩展点的抛异常测试模块。确认异常发生在部分资源已经分配之后。

- 分配前以 `long`/`checked` 验证所有相关乘积与合法容量，不能先溢出再转换。
- 初始化异常时释放已分配资源，保留可诊断错误。
- Manager 必须拒绝调度未完成初始化的状态；不能只信首块 buffer。
- 注意现有“配置修正后自动恢复”和“缺 shader 后探测恢复”路径，不能添加一个过早 return 将恢复入口永久挡住。

### 验收

- 中途失败后资源已释放，`IsAllocated` 为 false，后续帧不进入 GPU 派发。
- 不逐帧重复昂贵失败初始化，不持续刷异常。
- 修正配置或显式重开可恢复。
- 正常启动、重开、暂停、切场和已有 shader 恢复路径不回归。
- 不改变 GPU 结构体布局、正常导航或战斗算法。

## C. 遥测持续失败，旧占点样本仍可能累积至错误胜利

**优先级：P2；异常恢复专项。**

### 代码依据

- [BattleTelemetry.cs:247–273](../Assets/MassEngine/Diagnostics/BattleTelemetry.cs#L247-L273)：回读错误仅 return，不撤销旧 `snapshot.valid`；`sampleTime` 仅成功时更新。
- [HP 回读:342–374](../Assets/MassEngine/Diagnostics/BattleTelemetry.cs#L342-L374)也保留旧有效样本。
- [据点判断:807–845](../Assets/Game/Scripts/WarSandboxBattleController.cs#L807-L845)：只检查 valid/teams，不检查年龄，每帧用旧区域人数加 `Time.deltaTime`。
- [终局固化:848–858](../Assets/Game/Scripts/WarSandboxBattleController.cs#L848-L858)：写入战果并暂停。
- [设备哨兵:326–339](../Assets/MassEngine/Diagnostics/BattleTelemetry.cs#L326-L339)：其回读错误也直接返回，不能假定看门狗必然救场。

### 最小复现

构造两方有效参战，先注入一次单方占区有效样本，再让后续回读失败或停止提供新样本。真实占领状态变化后，推进时间超过占领时长，检查是否仍产生据点胜利。优先用可控样本/时间注入，不制造真实设备重置。

这是持续断流风险，**不是正常默认0.5秒采样延迟**。

### 最小修复方向

错误后标记遥测不可用或不健康；无新样本超过合理采样容差时停止胜负判断与占点推进，恢复有效新样本后继续。区分游戏暂停与遥测异常，明确时间基准；不能将无效样本改成零人数，否则会引入假全灭。不要对正常低频样本逐帧判失效。

### 验收

- 单方占点后回读持续失败/断流，超过占领时长仍不得错误结算。
- 无效遥测不会判全灭或平局。
- 新样本恢复后正常推进；正常采样、暂停/继续、倍速不回归。
- 结算只发生一次，错误状态有可诊断依据。
