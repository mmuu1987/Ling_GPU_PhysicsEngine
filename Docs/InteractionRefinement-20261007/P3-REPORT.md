## 1. 这次获得的结论

本节和对照表使用 `causal-01` 内同一夹具的两次原参数对照；`baseline-01` 是先行复现，保留独立原始结果，不混合或删选范围。

1. **默认案例不是出生时名义半径代理圆就重叠。** 初始与待命 1／3 模拟秒，名义半径重叠对数均为 0；最小 XZ 中心间距约 1.53467 米，大于两兵名义半径和 1.1 米。
2. **不接敌也会挤。** 只有一方执行移动、另一方远处待命时，30 秒已有 32–38 对深重叠，攻击者计数为 0；这一过程的网格桶溢出计数为 0。
3. **接敌会明显放大问题。** 原参数 40 秒有 560–606 对深重叠，且有 18–23 个桶超过容量。不能把重叠全部归因于敌方攻击，也不能把它全部归因于容量。
4. **增加桶容量不够。** 容量 18 → 72、cellSize 仍为 3，观测点的桶溢出归零，但接敌仍有 516–530 对深重叠。
5. **分离强度翻倍能改善重叠，但不是合格的直接修复。** 强度 24 → 48，其他 GPU 单位参数保持原值，接敌深重叠降至 170–184 对；然而战斗平均模拟时长增加约 **22.0%**，获胜方平均存活数减少约 **8.9%**，仍有残余深重叠。未把该实验值写回游戏。

方向已收窄到 **运行时推进、排队等待与软分离之间的竞争**。这是证据支持的定位方向，不是已经证明某一行代码就是唯一根因。半径翻倍、密度归一化和统一缩模型均未执行。

## 2. 固定条件与测量口径

- Green 正式场景，原有男战士／剑盾骑士，初始共 2048 人，两方各 1024。
- 半径均为 0.55 米，Agent 缩放均为 1，出生密度 0.4，宽深比 2.2，cellSize 3 米。所有条件保持这些值不变。
- 初始／待命、单军团移动、默认接敌三个阶段。移动目标为 (-20, 0, 0)，另一方待命；接敌使用现有 StartDefaultBattle。
- 固定 60Hz 模拟时钟；同阶段、不同实验条件使用同一固定近景相机，不替换引擎的 culling／LOD 相机。不同阶段焦点不同，已记录在 cameras.txt。
- 先完成两轮原参数复现，再在同一诊断夹具内完成三种条件各两轮对照。共 **98 个原始 GPU 快照**；独立 Python／KDTree 从 CSV 重新计算距离与成对阈值，98 个快照全部核对通过。
- 只统计 `hp > 0 且 state != Dead` 的活兵。截图可能仍包含尚未消退的尸体，不能把画面里每一处叠加都算成活兵重叠。

定义：名义重叠 `d < r_i+r_j`；软接触阈值 `d < 0.9(r_i+r_j)`；本报告的“深重叠”诊断线为 `d < 0.5(r_i+r_j)`，本案例等价于中心间距小于约 0.55 米。它是筛查指标，**不是引擎已有安全标准，也不是网格模型相交检测**。对数为无序对，一名士兵可能参与多对。

固定时间步和同步回读适合比较数值，不是实际帧率测试。以下“秒”均为本轮模拟秒，不能拿来直接对比 P0 的历史实时时长。两次重复仅报告范围，不宣称统计显著性。
