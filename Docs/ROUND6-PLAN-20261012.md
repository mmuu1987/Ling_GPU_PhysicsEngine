## 问题 1：前线拥挤度降得太多，想稍微挤一点

**你的描述**：拥挤度下降了，但降得多了些，可以稍微增加点拥挤。

**原因**：现在有四个机制都在往"散"的方向推，叠加后偏松。
1. **跟随间距**：向前的速度被限制在"离前面友军的空隙 ÷ 0.3 秒"，人走到刚好碰上就停，不允许挤进去一点点。
2. **R1 重叠修正**：只要有重叠就推开，直到完全不重叠。
3. **R4 侧向溢出**：被堵住就往旁边偏，把阵线拉宽、拉薄（强度 0.5，最多偏 0.7）。
4. **交战站位**：围攻位排在目标外一圈、贴着射程边缘（数据显示中位数 1.66 m，射程 1.8 m）。

**方案**：加一个总旋钮"拥挤度" `CROWD_PACKING`（0～1，默认先给 0.5），由它统一换算出四个参数，你只用说"再挤点 / 再松点"。

| 机制 | 0（最松，约等于现在） | 1（最挤） |
|---|---|---|
| 跟随间距允许压入 | 0 | 半径的 25% |
| 重叠修正容忍 | 0 | 15% 重叠以内不推 |
| R4 侧向溢出强度 | 0.5 | 0.2 |
| 交战站位距离 | 1.0 × 射程 | 0.75 × 射程 |

- 先做成 shader 常量，我按你的反馈改数，一轮几分钟；
- 定型后如果你需要，再挪进游戏设置里。

## 问题 2：身边已经有敌人，还往前挤去找远处的目标

**你的描述**：身边明明有敌人了，还会继续挤到更前面去找它锁定的那个敌人（你猜的）。

**你猜对了，代码就是这么写的**：
- 只有当前目标**失效**（死了、超出追击范围）或**过载**（围攻的人太多）时，单位才会重新挑目标；
- 当前目标只要还活着、没过载，身边贴着的敌人就不考虑；
- 即使重新评分，换目标也要求明显更好：门槛 0.18～0.73。距离分是按 12 m 的索敌半径归一化的，这个门槛相当于近 2～9 m 才肯换，贴身的敌人往往还不够格。

**结果**：
- 大量单位卡在第一排身后往前挤，自己却打不着（Attack 只占 1.6%）；
- 第一排被后面推着，阵线看着又挤又乱，后面的人又显得"闲"。

**方案：接敌优先**
- **规则**：没在攻击、当前目标又不在射程内时，如果身边接触距离内（射程 + 一点余量）有敌人，就改打最近的这个，门槛给得很小。
- **省开销**：先读一下自己所在格子的敌方密度。周围没有敌人就不做这次搜索，几乎不增加开销。
- **防闪动回潮**：正在攻击的单位不换目标；换目标的时机按单位错开，避免整群同一帧一起换。
- **预期效果**：
  - 更多单位就地开打，Attack 占比上升；
  - 单位会在第一次接触的地方停下来打，不再穿过去找远处的目标，前线会自然变"实"。这可能顺带缓解一部分问题 1，所以建议问题 1、2 一起调。

## 问题 3：漂移假象（其实在播走路动作，但动作太慢）

**你的描述**：其实是在播走路，但动作太慢，看着像漂移。想知道有没有参数能调"定住的时间"。

**原因（数据和代码都对得上）**：
- 走路动画的速度 = 实际移动速度 ÷ 参考速度（默认就是最高速度 6 m/s），再夹在 0.2～1.15 倍之间；
- 单位以 0.3～1.2 m/s 挪的时候，按公式只有 0.05～0.2 倍速，最后被夹在 0.2 倍：身体在走，腿几乎不动，看起来就是滑；
- 起步 / 停步阈值只有 0.12 / 0.05 m/s，很慢的蠕动也会被判定为"在走"；
- 后排还有"跑 0.5 秒 → 停 1 秒"的排队波（R2 只覆盖前线 16 m 以内，后排仍然走计时排队）。

**你问的参数，现在就有**：

| 参数 | 位置 | 现值 | 作用 |
|---|---|---|---|
| `moveStartSpeed` / `moveStopSpeed` | 兵种设置（UnitTypeGpuSettings 默认值） | 0.12 / 0.05 m/s | 起步 / 停步阈值（R1 的"站定死区"也用它） |
| `moveAnimationSpeedMin` / `Max` | 兵种设置 | 0.2 / 1.15 | 走路动画最慢 / 最快倍速 |
| `moveReferenceSpeed` | 兵种设置 | 0（等于最高速度 6 m/s） | 动画 1 倍速对应的移动速度 |
| `presentationHoldSeconds` | LOD 设置 | — | 画面上的动作至少保持多久才切换 |

**方案：要么站定，要么像样地走**
- **a. 加大站定死区**：起步 0.12 → 约 0.6 m/s，停步 0.05 → 约 0.3 m/s。慢于这个速度的单位直接站住、不动；重叠照样用位置修正推开，不靠"走"。
- **b. 提高动画最低倍速**：0.2 → 约 0.5。只要在走，腿就看得出在迈。
- **c. 新增"最短站定时间"**（建议 0.4～0.6 秒，可调）：站定后至少保持这么久，除非前方空出了一大块，专门消掉 0.3 秒一次的碎步。对称地加一个"最短行走时间"，避免走一两步就停。
- **d. 后排排队波（可选，等你看完 a～c 再定）**：
  - 方案一：把 R2 的连续跟随从前线 16 m 扩大到整个行军纵队，彻底取消计时排队；
  - 方案二：保留计时排队，只把等待时间缩短。

a～c 都是调参，或者是很小的改动，可以和问题 1 放在同一轮给你看。

## 问题 4（最严重）：框选下令后卡顿几秒，撤退 / 待命 / 移动 / 攻击都一样

**先说实话**：之前优化的是"整军命令重建流场时的掉帧尖峰"（改成异步，接受 1 帧延迟）。框选的局部命令从"点击到单位开始动"这一整段，在 1024 地图、11 万单位下从来没有完整测过。所以之前那次不算真正解决了这个问题。

**框选命令的完整链路**（`LocalOrderChannel` + `LocalOrderPlan`），每一步都有嫌疑：

| 步骤 | 内容 | 嫌疑 |
|---|---|---|
| ① 快照 | GPU 异步回读全部 11 万单位的位置和血量 | 通常几帧；GPU 很忙时会更久 |
| ② 规划（后台线程） | 按单位半径建导航网格（有缓存，但第一次或超过 5 种半径时要重建），再算 256×256 流场；攻击命令要对所有敌人算多目标流场 | 导航网格重建在森林地图（树多）上可能很慢 |
| ③ 攻击命令的自动重算 | 有攻击命令时，每 0.25 秒重新快照、重新规划一次 | **重算还没跑完时，新命令会被直接拒绝**（"请重试"），你再点一次就等于又等了一轮 |
| ④ 上传与确认 | 上传命令和流场，0.2 秒后回读一次确认 | 很小 |
| ⑤ GPU 起步 | 新命令到达后：清零速度 → 站定死区 → 跟随间距 | **密集队伍会一排一排地"醒"**：后排要等前排让出空隙才能起步，整团几秒才动起来。这条和这几轮的拥挤修改直接相关 |

**需要你帮我确认一个现象**：
- A. 画面本身卡住（帧率掉下来 / 冻住几秒）？这指向主线程的工作或某次同步等待。
- B. 画面流畅，但单位要过几秒才开始动？这指向 ①②③⑤。

**方案**：
- **第一步，先测，不猜**：加一份命令时间线日志，写到 `Logs/CommandLatency/`。每条命令记录：
  - 点击；
  - 提交；
  - 快照完成；
  - 规划完成（导航网格和流场分开计时）；
  - 上传；
  - GPU 确认；
  - 第一个单位开始动；
  - 一半单位开始动；
  - 这期间每帧的耗时。
  
  你按四种命令各点一次，我读日志，就知道时间耗在哪一步。

- **第二步，按测出来的瓶颈修**（候选做法）：

| 瓶颈 | 做法 |
|---|---|
| ① 快照慢 | 只回读被选中单位的数据（GPU 先收集），或者直接用上一帧已有的快照 |
| ② 导航网格重建 | 开战时就为所有兵种半径预建好，缓存不再清空 |
| ③ 被重算挡住 | 新命令直接取消正在跑的重算，不再拒绝；重算间隔按规划耗时自动放宽 |
| 主线程卡帧（A） | 把剩下的同步操作挪走，或分帧做 |
| ⑤ 逐排苏醒 | 收到新命令后的一小段时间（约 1 秒）里，同组单位一起起步：暂时放宽跟随间距和站定死区 |

- **不管瓶颈在哪，都先做到立即响应**：
  - 待命：当帧在 GPU 上生效，不需要等规划；
  - 移动 / 撤退：路线算好之前，先让单位朝目标方向转身、起步；
  - 选中圈和目标标记当帧给出反馈。
