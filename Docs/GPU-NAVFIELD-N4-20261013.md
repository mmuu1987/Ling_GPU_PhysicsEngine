# 导航 C · N4 报告（2026-10-13）

## 结论

N4（拥挤代价）完成，放在新的默认关闭开关 `gpuNavCrowd` 后面。

- **规则**：只把"堵住的本队士兵"计入代价，并且只作用于移动命令（点或区域目标）。追敌模式不受影响。
- **效果**：山口入口卡住的人数减少约 26%（879 对 1195），通过量与 N3 持平。队伍不再挤成一团，零损失，也不会碰到守军。
- **局限**：效果是温和的，没有出现"分流到另一个山口"。山口本身的宽度才是瓶颈，另一个山口在 440 m 外，按当前增益不值得绕过去。
- **测试**：138/138 通过。

## 关键设计：按"堵塞"计价，不按"密集"计价

**第一版**按人数计价，结果失败：
- 整齐行军的方阵本身就很密，整个方阵都变贵，于是向四周膨胀成一大团；
- 队伍一直摊到守军阵地，**攻方白白损失了 598 人**。

这正是以前记录过的死路："密度加权会让大部队自我排斥"。

**最终规则**：
1. **按真实速度加权计数**：权重 = 1 − 实际速度 / 畅行速度（限制在 0 到 1）。速度为 0 的计 1 人，达到畅行速度（默认 1.5 m/s）的计 0 人。全速行进的密集纵队不加价，堵住的人群才加价。
2. **交战不算堵塞**：正在接敌或攻击的士兵（以及阵亡的）不计入。
3. **只作用于移动命令**（点或区域）。追敌模式保持 N3 的场，接近和包抄由现有战斗逻辑负责。
4. **代价倍数按"当前格"计算**：该格所有出边一起乘 `1 + 增益 × min(堵塞密度/满载密度, 上限)`。这样三角形更新依然成立，增益为 0 时与 N3 逐位相同。
5. **EMA 平滑**（时间常数 0.5 s），防止两条路线轮流变挤导致来回摆。

**关于我的一次误判**：第一版的追击战里出现了两军之间的空白带和偏低的损失，我一度以为是拥挤代价造成的，于是加了第 2、3 条规则。后来对照发现，**最早的 N0b 基线（完全没有 GPU 导航）也有同样的空白带和低损失**，那是这个场景本身的波动。第 2、3 条规则在原理上依然成立，并且让 N4 的影响范围更小，所以保留了。追击战的帧时间也有两种状态（约 56 ms 和约 69 ms），不开 GPU 的基线两种都出现过，所以不能拿单次对比来判断性能。

## 配置（`Flow1024.asset`，需同时打开 `gpuNavField` 和 `gpuNavSteering`）

| 字段 | 默认 | 含义 |
|---|---|---|
| `gpuNavCrowd` | false | 总开关 |
| `gpuNavCrowdGain` | 2 | 满载时代价增加的倍数（满载时总代价为 3 倍） |
| `gpuNavCrowdFullDensity` | 1.5 | 每平方米多少人算满载 |
| `gpuNavCrowdCap` | 1 | 密度比的上限 |
| `gpuNavCrowdTimeConstant` | 0.5 | 平滑时间常数（秒） |
| `gpuNavCrowdFreeSpeed` | 1.5 | 达到这个速度（m/s）就不算堵塞 |

想要更强的分流，可以先把 `gpuNavCrowdGain` 调到 4 再观察。增益越大，越容易出现来回摆。

## 实测（森林丘陵）

**山口**：2 万人，GPU 转向开，LaneApproach 关，约 116 秒时的数据

| 版本 | 越过山脊 | 卡住 | 中位距离 | 与守军接触 | 攻方损失 |
|---|---|---|---|---|---|
| N3（无拥挤代价） | 289 | 1195 | 171 m | 无 | 0 |
| N4 第一版（按人数，已否决） | 390 | 243 | 143 m | **20 s 接触** | **598** |
| **N4 最终版** | 302 | **879** | 174 m | 无 | 0 |

最终版前 80 秒的队形与 N3 完全一样，说明正常行军不受影响。

**追击战**：11 万人，GPU 转向和拥挤代价都开。接敌 9.3 秒；平均帧时间 69.4 ms；75 秒时存活 104524 人。N0b 基线分别是 8.8 秒、69.8 ms、74 秒时 104656 人，一致。
