# UEBS2 路线对照与可借鉴优化（只读审查）

日期：2026-10-09。

## 结论

可以借鉴，最有价值的不是选框 UI，而是 **GPU 驻留的选择/命令状态、按组索引派发、共享导航场、按预算分帧模拟**。这些方向更贴近总人数 20 万的目标，但不能据此承诺我们的工程达到某个 FPS，也不能据此认为当前约 4.95 秒的 Editor 冷编译停顿会自动消失。

本轮仅通过用户新提供的 MCP 读取文件。没有写入对方工作区，没有运行游戏、Unity、编译或测试，没有修改或恢复我们工程的优化任务。此报告是当前工作区内的新分析文件。

## 1. 证据边界

新 MCP 绑定的是 `Ultimate.Epic.Battle.Simulator.Build.17640858/.../_analysis`。README 将它说明为 UEBS2 发行版的 C# 反编译、Compute Shader/DXBC 提取与重建分析，不是原作者的完整 Unity 源工程。

- `managed-src/Assembly-CSharp` 可核实 C# 调用和资源绑定。
- `compute-shaders/reconstructed` 包含可读或寄存器级 HLSL 重建，不应冒称原始 HLSL。
- 缺少场景/Prefab 序列化引用，字段默认值不等于游戏实际配置。
- `functional-status.md:3–14` 声明 60 个 kernel 在列出的确定性输入上通过差分；完整套件主要是 1×1×1 线程组。现有机器可读报告记录一个 seed、同样的线程组尺寸。它不是 20 万人战斗性能报告，也不是完整游戏行为证明。本轮未重跑这些测试。
- 未在本轮审阅材料中取得可核验的 20 万人 FPS、硬件配置、交战密度及持续运行报告。

## 2. 核实的技术路线

### A. 框选在 GPU，结果主要留在 GPU

`Army.cs:1601–1623`：先清选择计数，再传入队伍、相机参数、矩形和 order id，派发选择 kernel。

`GPUAI_UnitSelect.hlsl:29–104`：逐单位检查生命/队伍/RTS 权限与屏幕矩形；原子累加计数、写选中索引，并写入选中/取消选中事件。不能把 SendState 的事件编号简单当作永不消费的持久选择布尔值。

`Selectionrender.cs:40–67`：使用索引缓冲和间接实例绘制选中圈，不为每个单位创建一个圈 GameObject。

**对我们：GPU 框选并不是尚未采用的新技术。我们已有真实 GPU 框选与反馈，不能把问题误诊为 CPU 每帧 WorldToScreenPoint。真正需改进的是框选之后的命令准入与规划链。**

### B. 命令参数与单位状态分离，减少 CPU 全量往返

`FlyCam.cs:465–500`：设置 `CurrentOrder`、`CheckOrder`、`CheckSubOrder`，保留若干帧让 AI 消费。`Army.CancelOrder`（1590–1598）通过 GPU 选择 kernel 的取消分支处理旧命令。

`GPUAI_Behave.hlsl:33–51`：主 AI 读取 `AllOrders`、导航纹理、军队参数、组索引及单位状态。命令目标与单位命令属性没有要求 CPU 逐个回传全部士兵状态。

`Army.cs:2395–2457`：统计请求是 `AsyncGPUReadback.Request(KillCounts, 2000, 0, ...)`，回调取选中数、血量累计、攻击状态和军队统计。

**对我们：当前 LocalOrderChannel.Submit 会异步读回全体位置与 HP，CPU 规划完成再上传。可以研究 GPU 固定选择版本/成员集，CPU 只取得选中成员或必要目标摘要，最后由 GPU 绑定命令。但 Attack 的全军敌情和可达性检查也必须有对应摘要，不能仅删除回读就假装功能等价。**

作为数据量估算，20 万个 Vector2 位置加 int HP 是 2,400,000 字节/次，尚不含其他状态。这个字节数本身不是卡顿证明；调用频率、复制、同步和 CPU 算法才共同决定成本。当前使用的是异步回读，不应误称每帧同步 GetData。

### C. 按军队索引派发，而不是每个子任务都扫描所有人

`Army.cs:1657–1668`：建立该 Army 的 `MyAi` 索引缓冲，stride 为 8。

`Army.cs:1805、1961、2008–2012`：把它绑定为 `aigroup`，主 AI 和后续阶段按 `SpawnedAi.Count` 派发。

**对我们：这是非常直接的借鉴点。现有局部专用核仍按全体 agentThreadGroups 派发，再拒绝不属于该分区的线程。可研究按命令/兵种生成紧凑成员表及间接派发参数，让局部计算量更接近所选人数。该机制是我们从其“军队索引”设计推导的改进，不是声称对方已实现完全相同的动态选中分区。**

必须保留真实 agent ID 对应的 LOD cadence、每单位每帧恰一次处理、全局排除、死亡/取消/epoch 校验以及统一伤害快照和 swap。

注意：对方框选和取消本身仍是 O(N) GPU 扫描。一次廉价事件扫描与每帧重复执行重型战斗核不是一回事，不能笼统说“遍历全体就一定不可用”。

### D. GPU 共享流场与分帧预算

`NavGrid.cs:1374–1423`：目标写入、导航纹理绑定与 GPU 网格搜索；单位采样命令流场，不是每单位 CPU A*。

`Target.cs:144–159`：后续搜索在 Update 中执行 5 次或 1 次 FullSearch。

`ThreadManager.cs:1566–1679`：累计 Army 人数、计算 GoalAiPerFrame，达到预算后暂停继续派发，后续帧推进；WorldDelta 对跨帧更新进行补偿并设上限。

**对我们：已有共享流场和 LOD，因此不是从零采用这些技术。应比较“何时建图、共享到什么粒度、哪个系统受帧预算限制”。可以优先拆分不可变导航拓扑与独立求解工作区，避免重复构图；再评估 GPU 增量流场以及受控的决策频率。**

不可直接共享非线程安全的 TerrainNavigationGrid 工作数组。将部分决策分帧也不能自动保持 DPS、移动速度和高速弹丸碰撞正确；渲染帧率高不等于每个单位每帧高精度完整更新。

## 3. 附带文档不能照单全收

阅读了 `rts-gpu-selection-command-system.md`，并与代码交叉检查，至少需要修正以下说法：

1. **“CPU 从不遍历单位”过强。** `Army.cs:2134–2156` 的 CheckForAliveAi 分支同步读回 AllAi 并遍历；这是条件路径，不应再反过来误写成每帧必然发生。
2. **“只读几十字节”不准确。** 当前代码申请的是 2000 字节统计回读；缓冲创建为 500 个 int。仍然远小于全体单位状态，但应按真实大小描述。
3. **“全程分帧寻路”不准确。** `Target.StartSearch` 直接调用 TargetSearch；`NavGrid.cs:1508–1538` 在同一次调用内循环 EndIteration 并反复 Dispatch。后续 FullSearch 分帧，不代表首次提交天然无尖峰。
4. **“每两帧更新选中圈”不符合当前代码。** Selectionrender 的 cnt 达到 2 后没有复位，此后在条件满足时会继续更新。文档示例补了复位，不能视为原代码。
5. **选中索引容量需要保护。** RenderAmount 默认 1000，但 Inspector 可能覆盖。当前重建 UnitSelect 写 SelectRender[selectionIndex] 未见容量钳制，绘制实例数也直接使用 SelectionState；不能简单解释为“超出时少画几个圈”。需确认实际资源与边界行为。
6. **线程组取整有待核实的风险。** GlobalTotalAi 为 int，SelectAi/CancelOrder 写的是 `CeilToInt(GlobalTotalAi / 32)`；若总人数未预先补齐至 32 倍数，整数除法先截断会遗漏尾部。应使用正确向上取整并保留边界检查，不机械复制。
7. **手写投影不是优先优化项。** 相机矩阵的上传量很小；手写投影还需正确处理近裁剪、相机背面、正交相机及不同 viewport。本文档示意投影与重建实现也有细节差异，不能作为替换依据。
8. **10 帧广播不是可靠事务协议。** 它依赖分帧调度窗口；我们应保留/完善 sequence、epoch、确认及取消的幂等语义，不能为省事删除已有保护。

此外，该工程也存在人数变化时销毁重建 MyAi 等资源的路径；静态全局状态和魔数较多。这些不是应当复制的部分。

## 4. 能否解决当前性能问题？

需要分别回答：

| 问题 | 借鉴价值 | 尚不能得出的结论 |
|---|---|---|
| 20 万人的命令下发与持续模拟 | GPU 驻留状态、按组派发、预算调度很有针对性 | 未经基准不能承诺 20 万人 FPS |
| 约 330ms 的首次 CPU 规划 | 避免重复建图、减少全体状态往返、增量求解值得验证 | 不能断言换 GPU 导航就降到某个毫秒数 |
| Editor 首次 Attack 约 4.95 秒编译停顿 | 清晰阶段边界和较少重复展开可以帮助重构 | 仅将选择结果留 GPU 并不会自动缩短 shader 编译 |
| 冷态进场约 44 秒 | 必须继续分段归因，关注全局核与资源初始化 | 对方发行版预编译 DXBC 不证明其源码冷编译很快 |

对方也有复杂的 Behave 主 kernel，不能从“有 21 个 GPUAI kernel”推导成“所有工作都拆成简单小核”。发行版运行与我们的 Editor 冷缓存测试也不是同一条件；Player 仍可能有驱动首次创建成本。

## 5. 推荐的取舍与验证顺序（尚未实施）

不建议因为当前实现卡顿就直接删除框选。优先保留用户价值，评估替换其后较重的数据路径：

1. 冻结第三版作为正确性对照，不继续叠加未经预算的细节优化。
2. 先做无局部指挥的底座容量曲线：2048、1 万、5 万、10 万、20 万，区分行军、稀疏接战、密集接战和远程；同时记录硬件、CPU/GPU 帧耗时、显存、逻辑 tick 和冷/暖状态。
3. 一个可独立回退的候选只改“紧凑成员索引＋按成员数量派发”，比较选四、选千人、选万人时的成本，并验证不重复、不漏算和边界安全。
4. 另一个候选减少命令对全体 CPU 快照的依赖，使用选择版本和明确完成确认；不要同时重写全部战斗逻辑。
5. 最后按实测决定是否改 GPU 增量导航/预算调度。必须保留或重新验证原有墙体、切角、边界、局部半径掩码和射界语义。

借鉴架构应独立实现，而不是把反编译代码整体搬进我们的工程。若最小候选也超出预算，再限制同时活跃局部组数、选择规模或暂缓部分命令，而不是先假定必须砍掉框选本身。

**总判断：值得借鉴其数据流与预算思路，尤其是 GPU 驻留命令和按组索引派发；不值得照搬魔数、广播窗口、未保护的固定容量或文档中的性能承诺。本轮仅完成静态审查。**
