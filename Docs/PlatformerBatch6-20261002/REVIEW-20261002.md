## 发现

### R1 · P2：原候选续做入口仍从第 5 批继承，不能直接用于当前版本的继续扩充

位置：

- `Assets/Game/Editor/CharacterPipeline/Troops6Builder.cs:28–30`
- `Assets/Game/Tests/EditMode/Troops6PreparationTests.cs:30–34`

`RegularPolicyPath`、`BaseCatalog` 仍指向 `Troops5Builder.Integrated`，准备测试也固定要求 19 个模板。当前实际已完成的 Platformer 集成库有 22 个常规模板、26 个条目。

**触发条件：** Birb / Bunny / Fish 来源恢复后，直接沿用这个旧候选入口作为下一版的扩充基础。其新库会缺少已发布的蟹怪、小怪、骷髅头；随后沿用当前正式目录条目列表准备新版本，会出现源条目缺失，而不是正确追加新角色。

**建议：** 真正启动这三个原候选时，先把继承基础切到已完成的 Platformer 集成库，并补“全部旧条目 / 旧模板身份保留”测试。新输出、目录版本、Build 入口使用新名字；不要覆盖 Version06。来源仍未解决前，不执行准备或整合。

这是未来续做风险，不是当前 Version06 的运行时缺陷。

### R2 · P2：方案测试的构建列表恢复依赖外部运行器

位置：`Assets/Game/Tests/PlayMode/PlatformerBatch6PlanCycleTests.cs:22–31,55,75`

`IPrebuildSetup.Setup()` 先覆盖 `EditorBuildSettings.scenes`；进入 Play 后的 `UnitySetUp` 才保存 `oldScenes`。所以 `UnityTearDown` 恢复的是已经替换过的测试列表，不是测试开始前的正式列表。

现有 `Logs/AgentPlatformer6/run-plan-cycle-02.cjs:13–22` 会在进程退出后恢复原文件，因此既有运行器下的成功记录并不矛盾；但直接使用 Unity Test Runner / 另一条 CLI 路径时，不能指望这个 fixture 自己恢复正式配置。

**建议：** 在 Prebuild 修改前保存基线，并使用可靠的测试后清理机制恢复；要考虑 Editor 域重载和测试失败路径。外部运行器的文件备份继续保留作为第二层保护。修复后验证成功和失败两条路径均恢复原 Build Settings。

当前普通试玩不运行该 fixture，不因此阻塞当前包。

### R3 · P2：重跑战场测试会覆盖固定名称的历史证据

位置：`Assets/MassEngine/Tests/PlayMode/PlatformerBatch6BattlefieldTests.cs:25,39,96,124`

测试固定使用 `platformer6-battles-01`，并通过 `File.WriteAllText` / `File.WriteAllBytes` 覆盖 JSON 和截图。即使外部运行器使用新的日志 tag，测试内部仍写原来的证据文件名。

**触发条件：** 为 review 或回归再次运行该 PlayMode fixture。旧验收截图与战果会被新结果覆盖；这不符合保留历史证据的要求。

**建议：** 由运行器传入独立 run ID / 输出目录，开跑前拒绝占用已有输出，并使用不覆盖写入。第一轮证据保持只读。本次没有重跑该 fixture，避免制造这个副作用。
