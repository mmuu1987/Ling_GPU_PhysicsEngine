# 兵种模型制作管线（M5.4 内部制作手册）

## 多骨架骑乘组合（2026-09-30）

许可选择未明确时不默认引入新CC BY-SA，采用既有CC0人物和CC0马派生制作。用坐骑Torso建立鞍位、骨盆跟随、两骨骼腿部约束和统一动作时间轴；缰绳跨两骨架绑定但烘焙后仍一个常规VAT单位。对实时约束姿态→序列化clip→VAT分层核对，骨骼目标接触与网格视觉接触分开表述。

骑手/马整体倒地，无落马/上下马逻辑。骑乘尺寸较巨兽小，应给专用匹配中心接敌对照，不直接套最大巨兽距离。成功几何不因上下文修改重复烘焙；既有管线/核心不改。详见[本轮证据和局限](../../Docs/Cavalry-20260930/README.md)。

## 已定原点输入不要重复声明待标准化根（2026-09-30）

蜘蛛限时只读完整诊断：已准备最终坐标直接RGBAHalf编码2.38856mm，最坏点与数学Half一致，能过2.5mm。旧sizeRootPath声明使通用流程先移走已完成的ScalePivot平移，再补回，在另一坐标范围量化后精度不可恢复。原有代码不用改；新的已单位缩放/已居中落地输入用空sizeRootPath、ground=false，实际bindheight作为target。Spider04全门禁通过，旧失败不改写。

新恐龙同样在准备层定尺寸/原点，保留来源动作/固色材质，仍走原Gate/Low/检查。直接挂到统一库新大型policy及场景，旧角色列表/config只读保留；不把反复转换或放宽容差当成修复。详见[非人形第二批](../../Docs/NonhumanBatch2-20260930/README.md)。

## 从角色资产到实际布阵角色库（2026-09-30）

旧RuntimeDeployment.Templates来自初始Scenario，Catalog注册不等于可选。本轮新增可选战场RosterPolicy：显式模板库+安全默认人数/阵型+占地/网格/人数限制，null保留旧行为；真实UI模板/新增/撤销/取消与混合计划保存重载、live渲染绑定都要检查，不能只看配置列表。

常规12种可同场，大型2身体在受限场用适配对照，未实现大兽任意互斗/密集混编。原男/女/UnityChan不重烘焙；Sazen骷髅只复制原FBX到新命名空间，实采原变换校验通过后UV图集/四槽/LOD。原PBR/Polyart风格变体不虚增独立模型数。详见[统一角色库说明](../../Docs/UnifiedRoster-20260930/README.md)。

## 大型四足适配边界（2026-09-30）

不以简单显示缩放代替物理：本批按最长地面跨度约6m定尺寸、水平居中，动画活跃帧取保守圆半径；因分离固定邻域1圈，新场景私有cellSize≥两半径之和，稀疏手动阵型，近战中心距离须让双方都能触及。不是改成胶囊/精确腿部碰撞，不能据此保证窄通道或所有地形。

无UV纯色材质转新线性色板时按材质边界复制必要顶点，保留new→original映射供逐帧源位置核对。放大尺寸和原点前移到Half编码前，仍保持2.5mm门禁。狼/公牛通过，Spider攻击3.78mm暂缓；原生未量化BakeMesh/LBS一致不代表VAT也通过，不武断定因或降低标准。

正式配方LargeWolf02/LargeBull02；新验收钩子做实际Move/Hold短检查并Reset，再跑自然结算。默认旧验收64/96不变，小场景8/12。详见[大型兽形说明](../../Docs/LargeBeasts-20260930/README.md)。

## 不同作者静态缩放输入准备（2026-09-30）

Quaternius三怪物导入为100倍静态层级，蘑菇腿带微小非均匀数值误差。公共门禁不放宽；专用准备器将自有顶点/法线/bindposes与单位缩放层级一致化，按原动作世界姿态生成局部曲线，原始LBS→准备后每烘焙帧核对≤0.25mm，再走原VAT≤2.5mm检查。只接受常量导入scale及相对rest≤0.02%数值噪声，真实缩放动画仍拒绝；不是任意骨架重定向。

32×32原色板需显式配置，不能套KayKit4×4。新3种配方Orc/Yeti/MushroomKing，各78帧@24FPS。准备器中途错误回执留存，Unity recently-deleted GUID路径也视为不可覆盖：另建Prepared02，不放松ValidateNewPath。

新六场目录复用前批旧场景/配置只读；完整范围/原件许可标题说明见[本批文档](../../Docs/EnemyBatch2-20260930/README.md)。

## 三敌方模型批量复用（2026-09-30）

用户明确优先扩充模型，而非另开玩法。SkeletonWarrior/Rogue/Mage三个独立身体复用现有配方核心；原FBX中的刚性头盔、帽子、兜帽/披风也必须明确登记attachmentPaths，不能仅登记新武器。

法杖的导出轴和握持手不能照搬剑盾假设：本批保留01/02检查版，最终Mage03按Idle手坐标校准长轴，原网格/身体骨骼/核心不变。三模型Low显式2000预算，24FPS、每种纹理≤32MiB，未修改聚类算法凑数。

新批次聚合器生成3场景目录与稳定身份，一包选择；单模型仍走原配方，不复制改写通用烘焙器。只对已有Medium骨架素材做这批验证，不推论任意角色自动重定向。完整支持边界与证据见[本批说明](../../Docs/EnemyModels-20260930/README.md)。

## 有界形变附件与朝向检查补充（2026-09-30）

Ranger弓使用单一Draw Blendshape，原默认拒绝规则不能靠丢弃形变绕过。新增Recipe.blendshapeAttachmentPaths显式白名单，只允许零骨骼/无bindposes/单形变/单100%线性帧附件，绑定必须精确匹配、键值及实际采样权重0–100；其他Blendshape仍拒绝。参考位置=M×(p+w×delta)，原生0/50/100核对与旧骑士04回归通过。显示身高不把声明的弓/箭形变附件算入身体高度。

数学门禁不能发现语义挂点错误：Ranger01曾弓弦拉向外、箭轴竖向；02按实际持弓/持箭手坐标校准后另建产物，原始弓网格/形变不改。必须查看拉弓/松弦近景，不以“有动画/无粉色”替代。手持箭收拢形变只是呈现，实际弹道仍来自现有系统；只近似同步，不做逐帧/骨骼发射承诺。

最终配方Ranger02.asset，已有目录不得覆盖；[支持边界、校准和真实发射证据](../../Docs/RangerPilot-20260930/README.md)。仍未证明跨作者重定向或大型生物适配。

## 2026-09-30 骑士缩放陷阱：不能仅凭无粉色/有运动验收

在本次准备层级 `ScalePivot=.7077963` 下，实测 `BakeMesh(mesh,false)` 后再做renderer→root转换会重复缩小各蒙皮部件，形成LOD0头颈间隙。原模型完整，VAT只是保存了错误几何。不要下移头部或补脖子掩盖。

骑士私有03配方：单位缩放临时实例进行生产烘焙，再对完整Full位置纹理、clean mesh和bounds做一次正向均匀缩放/平移，然后减面生成Low。此法不声称支持非均匀/负缩放；通用VatBaker未改。门禁新增全部114帧、Full6666顶点对独立bones/bindposes/weights蒙皮，最大误差约1.194mm；同机位GPU图需人工审看头颈/肩/手与挂件，不能被可见性/运动检查替代。

## 1. 产物与职责

```text
Unity 已导入模型 + Idle / Move / Attack / Death + 显式附件
  -> MassEngine/VAT Baker
  -> 新 VATProfile.asset（内含 cleanMesh、位置/法线纹理、可选 Low LOD）
  -> MassEngine/兵种绑定向导 + 已保存的数值模板
  -> 新 UnitTypeConfig + 独占 Spawn/Combat/RenderConfig
  -> 测试战场 Scenario 编成 + BattlefieldCatalog 稳定模板登记
  -> Windows 开发构建 -> 玩家布阵 -> 开战 -> 自然结算 -> 重开
```

| 层次 | 负责什么 | 不负责什么 |
|---|---|---|
| VATProfile | 固定顶点顺序的网格、位置/法线纹理、四段帧窗口 | 战斗数值、材质贴图、军团身份 |
| RenderConfig | profile、near/mid/far 网格与三个材质/阴影槽位 | 从源模型自动制作材质或图集 |
| UnitTypeConfig | 兵种实现类型、名称、teamId 和各子配置引用 | 自动进入所有战场/玩家模板目录 |
| ScenarioConfig.unitTypes | 该场景默认部署的编成清单 | 存档的稳定模板 ID |
| BattlefieldCatalog.templates | templateId + revision 到兵种资产的映射 | 自动把兵种加入玩家配兵下拉或默认部署 |

## 2. 源模型准备

### 2.1 建模、绑骨与导入

- 推荐使用单独的 Prefab 资产作为输入；窗口也接受场景对象，但可复用输入不应依赖未保存的场景修改。
- 烘焙器自动收录模型层级内**启用且节点激活**的 `SkinnedMeshRenderer`。隐藏的换装件不会自动加入。
- 所有网格必须非空、使用三角形拓扑；蒙皮骨骼不能缺失或指向模型层级外，非空 `rootBone` 也必须属于模型层级。
- 四段动画中顶点数量、顺序与网格引用必须稳定，不能通过替换 sharedMesh 或拓扑变化制作动画。
- 在 Unity 导入器/预览中先确认骨架与四段 clip 匹配。现有内置 Humanoid 与手工两骨骼蒙皮已有工具级测试，但不等于任意新模型自动兼容；烘焙器不会替你修 Avatar 或重定向错误。
- FBX 可走 Unity 原生导入；其他格式须先经工程支持的导入流程变成 Unity 模型/AnimationClip。本工具本身不是 glTF/外部格式解析器。
- 不把 FBX 的 `Read/Write` 关闭直接判为缺陷：现役内置 FBX 在 Editor 烘焙路径已有可读实测。以本次导入结果和工具实际错误为准。

### 2.2 坐标、比例与移动

- 制作基准建议采用 Unity 的 **Y 向上、Z 向前、1 单位约 1 米**，脚底位于局部地面附近；与内置士兵同场检查身高、武器尺寸和脚底高度。
- 烘焙在模型根局部空间采样；每段采样副本的根节点被设为位置零、旋转单位、缩放一。**不要靠拖动 Prefab 根的 Transform 缩放/旋转来交付最终尺寸朝向。** 在导入或模型子层级整理好几何与骨架基准。
- 推荐在源工具中应用变换并使用正的单位缩放；非均匀/负缩放不是本手册推荐路径。代码拒绝零缩放、不可逆矩阵、NaN/Infinity 与超出半精度位置范围的采样。
- 引擎负责世界移动和朝向，Move 推荐原地循环，避免把持续前进位移烘进骨骼动画造成脚滑/相对 Agent 漂移；Attack 和 Death 也要检查根位移。
- `RenderConfig` 没有额外模型缩放/朝向补偿字段。不要靠修改碰撞半径掩盖模型比例问题；与模板的物理尺寸、移动速度、近战距离分别对照。

### 2.3 UV、纹理与单材质约束

- `VatBaker.BuildTopology` 保留各源网格 UV0，把全部源网格/子网格三角形合到**一个 submesh 0**；运行时每兵种每 LOD 一次绘制，只用该档一个材质。
- **不会保留原模型多材质槽映射、不会自动打图集、不会自动复制源材质。** 多材质模型须预先整理到同一图集/兼容 UV，或接受统一材质的效果；不要期待不同 submesh 继续使用不同贴图。
- 现役 VAT shader 使用 `_BaseMap` 与 `_BaseColor`；VAT 法线纹理是逐顶点动画法线，不是材质法线贴图。源模型的完整 PBR、多层透明等效果不会因烘焙自动复现。
- 从在用 VAT 材质复制出试验材质，再设置自己的底色图；近景使用现役光照 VAT shader，中/远景可复用无阴影 VAT shader。三个材质槽都必须有引用，即使 mid/far 共用网格也不能留空。
- 位置/法线纹理是数据：工具生成 **RGBAHalf、线性、无 mipmap、Point、Clamp**。不要转成普通压缩色彩图、改尺寸或用另一份网格替换对应 LOD。
- 网格、纹理和窗口是一套绑定产物。编辑烘焙网格的顶点顺序会破坏 `vertexID -> texel` 映射；改源模型后应另存新烘焙版本。

## 3. 四段动画规格

| 槽位 | 制作要求 | 当前工具语义 |
|---|---|---|
| Idle | 站立待机，循环接缝自然 | 循环 |
| Move | 原地行走/奔跑，与模板移动速率相称 | 循环；运行时可按移动速度调整播放速率 |
| Attack | 一次可重复攻击动作，不靠根位移推进 | 循环；战斗数值仍来自 CombatConfig |
| Death | 从站立到倒地，末姿态稳定 | 单次，采样包括末帧；shader 钳在末帧 |

四个 `AnimationClip` 全部必填。默认 30 fps，可选 1～240；按 `max(1, ceil(clip.length * rate))` 的 float 口径计帧，四段连续排列，总帧数上限 16384。
零长 clip 在代码上可成为一帧，但静态占位不能作为“四段动作已验收”的证据。

工具不使用 Animator Controller 的状态机来拼动作，而是逐帧 `SampleAnimation`，再对蒙皮执行 `BakeMesh`。
每段重新实例化同一个模型基准，`cleanMesh` 在采样前保存绑定姿态，不是 Idle 首帧。

## 4. 显式附件与烘焙

### 4.1 附件不能漏

武器、头发、眼睛、盾牌等若是 `MeshRenderer + MeshFilter`，必须展开窗口的
**“附加 MeshRenderer（武器等非蒙皮部件）”**逐项加入。它们须来自所选模型自身/子层级，启用且激活；外部对象、空引用不合法。
附件的骨骼挂点变换会被逐帧采样，不必伪装成蒙皮；重复选中同一附件会被去重。

内置 Male 重烘参照的显式附件是：`Hair01`、`Head01_Male`、`Shield08`、`Eye01`、`Mouth01`。
这份列表不是通用模板；换模型必须按实际激活部件重新选择。

### 4.2 窗口步骤

1. 停止 Play Mode，打开 **MassEngine/VAT Baker**。
2. 指定模型、四段 clip、采样帧率和显式附件。先在模型预览核对动作/部件，避免只看烘焙摘要。
3. 首次保留默认 Low LOD：比例 0.25、顶点上限 1200。上限 0 表示不限，非零须至少 3；聚类产出不是“恰好某个顶点数”的承诺。
4. 选择 `Assets/` 下**已经存在**的试验目录，填写未占用的新资产名；点击 **烘焙到资产**。
5. 检查摘要中的顶点、总帧、布局、Low LOD。产物是一个 profile 主资产和配套网格/纹理子资产，不必手工拆散再接引用。
6. 源模型/动画修改后使用新名字再次烘焙；确认外观与回归结果后再决定是否替换引用。不要覆盖旧基线或删除历史遗留 SuperLow 资产。

`VatBakeResult.SaveNew` 只接受新的 `Assets/... .asset` 路径；已有文件、同名 `.meta` 或资产引用均拒绝。失败回滚本次资产，`Dispose` 清理未持久化对象。
脚本接入用 `using (var result = VatBaker.Bake(request)) { result.SaveNew(path); }`，先落盘后绑定。

预算守卫是工具边界，不是推荐制作规格：总顶点最多 100 万、索引最多 600 万、纹理任一尺寸最多 16384、估算工作内存最多 512 MiB。
超预算优先降低模型顶点/动画长度/采样率，不为一个试验模型扩引擎契约。

## 5. LOD 配对与绑定

当前烘焙器只生成 Full 和可选 Low，**不生成 Mid**；现有 profile 契约支持 Full/Mid/Low。
绑定向导与运行时采用同一规则：

| profile 内容 | near | mid | far |
|---|---|---|---|
| 只有 Full | Full | Full | Full |
| Full + Low（新工具常用） | Full | Low | Low |
| Full + Mid | Full | Mid | Mid |
| Full + Mid + Low | Full | Mid | Low |

现役 Male 为 Full + Low；Female 有有效 Mid/Low。目录中的 `SuperLowLOD` 遗留资产不是第四个运行时槽位，M5 不需迁移/清理。
观测距离以测试场景的 `LodConfig` 和实际 lodCenter 为准；当前默认 near 30、mid 120、最大绘制距离 500，远距离死亡单位不进入 far 桶，不把它误判成 Death 烘焙丢失。

### 5.1 推荐：新建试验兵种

1. 先准备独立的测试场景/Scenario；**不要使用默认 11 万部署作为新兵种登记目标**。
2. 打开 **MassEngine/兵种绑定向导**，手工确认“战役配置”确实是测试 Scenario。窗口自动找到的配置不能代替人工核对。
3. 选择已保存、能正常渲染的内置 `UnitTypeConfig` 作为数值模板，填写试验兵种名、军团编号、已存在的输出目录。
4. 选择已落盘的新 VAT profile，勾选 **独占 RenderConfig**，点击 **新建并绑定**。
5. 查看完整校验结果；“资产已新建”不等于通过，缺材质等错误可能在新建之后显示，须修正后再次校验。
6. 三个材质通常从模板 RenderConfig 复制而来；新模型 UV/图集不同时应改为独立材质。绑定不会自动修改材质。
7. 调整新 Spawn 的人数/出生位置与新 Combat 的数值。`teamId` 同号是同一军团，允许混编；范围 0～7。“下一个空编号”按钮仍需确认没有落到已占用编号。

新建会独占 UnitType、Spawn、Combat；勾选时独占 RenderConfig；Movement/Flocking/Animation 按模板共享。
**独占 RenderConfig 不代表其 Material 也自动复制。** 如果要改共享动画速率、移动参数或材质，先显式复制相应资产，避免连带修改内置兵种。
新建后自动追加 `ScenarioConfig.unitTypes`，但不自动登记玩家模板目录。
未传 profile 时可能继承模板原绑定，不能把“没传 profile”理解为“新兵种无模型”。

### 5.2 修改已有试验兵种

选中兵种，检查共享 RenderConfig 提示，然后“绑定到选中兵种”。该操作整体写入 profile 与三个网格槽，不创建材质。
同一 RenderConfig 的所有使用者都会变更；提示统计的是当前 Scenario 中的使用者，不代表工程内全部引用。
如只想换一个兵种，先复制 RenderConfig 并改其引用，再绑定。

窗口负责 Undo、标脏和保存；核心 `UnitTypeBinder.Bind` 返回校验结果，本身不是“校验失败即撤销”的事务，窗口也会提示“绑定已写入，但校验未通过”。
`ValidateBinding` 是只读检查，涵盖兵种配置、profile 契约、网格配对、三个材质非空与移动动画速率区间；它不判断美术正确或 shader 实际外观。
材质非空但用了错误 shader，仍须运行时观察；不要把校验绿灯当作外观验收。

## 6. 登记默认编成与玩家模板：两步都要做

**仅把资产放入文件夹不会自动上战场；仅登记 Catalog 也不会自动出现在玩家配兵下拉。**

1. 试验场景的 `MassEngineManager.scenarioConfig` 引用测试 Scenario；该 Scenario 的 `unitTypes` 包含试验兵种和至少一个敌方编成。新建向导已追加清单，但仍须核对场景指向。
2. 调整试验人数和出生中心，确保脚印不重叠、不越界、不落入障碍；在制作工具里明确操作并保存，不覆盖已验收默认场景/六个编成。
3. 在测试入口使用的 `WarSandboxBattlefieldCatalog.templates` 添加 `WarSandboxUnitTemplateEntry`：
   - `templateId`：稳定、非空、无首尾空格、目录内唯一，例如 `m54-trial-sword`；不要把显示名/Unity InstanceID 当稳定 ID。
   - `revision`：正整数，首次 1；不兼容模板变更需明确递增并接受旧方案不兼容。
   - `config`：新 UnitType 资产；同一 config 不能登记多个不同 ID。
4. 给测试场景配置合法战场条目（稳定 id、显示名、scenePath、rules、正的内容/地形版本），加入构建；保留原战场和模板条目。
5. 检查 `TryValidateTemplates`、`TryResolveTemplate` 与 `TryGetTemplateId` 对新模板通过，并保证原有编成也有稳定映射，否则含它们的方案仍无法保存。

关键实现：`WarSandboxRuntimeDeployment.TryBeginEdit` 首次从 SourceScenario 的已部署编成收集 `Templates`，不是遍历 Catalog 的全部模板。
运行时草稿的模板还必须在这份允许清单中；Catalog 负责保存/载入时的稳定映射。因此试验流程需要“Scenario 收录 + Catalog 登记”两条链。

玩家应用布阵只创建运行时 Scenario/UnitType/Spawn 副本，Combat/Movement/Animation/Render 等仍只读共享。
`TryApply` 校验后重建 GPU，失败恢复上一版；`TrySavePlan`/`TryLoadPlan` 需要当前入口会话与对应 Catalog。
直接打开战场场景可以观察模型，但不能代替有战场身份的独立构建保存/载入验证。

## 8. 入口与排错速查

| 症状/操作 | 先检查 |
|---|---|
| 武器/头发不见 | 显式附件列表、节点激活与 renderer.enabled，是否同一模型层级 |
| 花屏/顶点飞散 | 网格与该 LOD 的 VAT 纹理是否同一套，是否更改顶点顺序 |
| 模型静止但尺寸校验全绿 | 实际 clip 能否驱动该模型；逐帧纹素/真实渲染是否变化 |
| 某个距离整批消失 | 三个材质引用、对应 VAT shader、LOD/剔除半径；死亡远景另有剔除规则 |
| 模型尺寸/朝向不对 | 源模型根局部基准与导入变换，不要期待 RenderConfig 自动修正 |
| 新建后没有兵 | 场景实际引用哪个 Scenario、清单与 Spawn 人数/实现类、重载后引用是否为空 |
| 玩家下拉没有新模板 | 新兵种是否在该场景 SourceScenario 的初始编成中，不只看 Catalog |
| 方案无法保存/重载 | 是否通过目录进入、全部编成的 templateId/revision、战场/地形版本是否一致 |
| 绑定后模板也换了模型 | RenderConfig 共用；独占 RenderConfig 内的材质也可能仍共享 |

关键源码（便于后续维护，API 以实现为准）：

- `Assets/MassEngine/Editor/VatBaker.cs`：`VatBakeRequest`、`VatBaker.Bake`。
- `Assets/MassEngine/Editor/VatBakeResult.cs`：`SaveNew`、`ValidateNewPath`、`Dispose`。
- `Assets/MassEngine/Editor/VatBakerWindow.cs`：菜单与四段/附件/Low LOD 表单。
- `Assets/MassEngine/Editor/UnitTypeBinder.cs`：`CreateUnitType`、`Bind`、`ValidateBinding`、`ResolveLodMeshes`。
- `Assets/MassEngine/Editor/UnitTypeBindingWindow.cs`：菜单、保存/Undo、共享引用提示。
- `Assets/MassEngine/VatRender/ResolvedUnitTypeRuntime.cs`：网格/纹理配对、材质与窗口初始化。
- `Assets/Game/Scripts/WarSandboxRuntimeDeployment.cs`：`TryBeginEdit`、`TryValidate`、`TryApply`、`TrySavePlan`、`TryLoadPlan`。
- `Assets/Game/Scripts/WarSandboxBattlefieldCatalog.cs`：`templates`、`TryValidateTemplates`、`TryResolveTemplate`、`TryGetTemplateId`。
- `Assets/Game/Editor/WarSandboxEntryBuilder.cs`：`BuildWindows`，常规开发构建输出 `Builds/WarSandbox/WarSandbox.exe`；`CreateEntry` 不会自动替已有目录补新兵种。
- `Assets/Game/Scripts/WarSandboxEntrySmoke.cs`：现有开发构建烟测/截图骨架；完整对局/UI 自动检查与人工验收分开记录。

任何 Unity 执行必须使用有效工作树，并串行处理同工程任务；不要加 `-nographics`。
非阻塞小瑕疵按工程约定记入后续项，不为制作手册扩大引擎重构范围。


## 已执行案例：KayKit Knight（2026-09-30）

- 官方Adventurers Free2.0 + Character Animations Free1.1，CC0；Knight/单手剑/盾/atlas及General、MovementBasic、CombatMelee，只选9份源文件。
- Generic路径每段240条曲线匹配；四动作Idle_A、Running_A、Melee_1H_Attack_Chop、Death_A；骨架外挂缩放节点避免根归一化抹掉尺寸。采样脚尖方向验证+Z，不用打开的面罩包围盒猜朝向。
- 生产Full VAT为6666顶点/114帧；通用空间聚类会跨atlas色块平均UV，像素“可见/非粉色/可动”仍可能串色。本例使用**仅适配作者4×4调色板**的`KnightAtlasLodBuilder`，Low1337顶点/2299三角形，重做12组48帧真实GPU检查；不要盲用于其他atlas或据此修改旧角色。
- 当前Attacker模板已有远程参数：只换模型不会变成近战。第一包截图捕获到错误继承，最终02将**私有**Combat projectileRange置0并提升模板revision2，重新跨进程验证。也要检查相机全景和共享模拟参数，不能仅看静态资源已生成。
- 最终profile是`Assets/Game/CharacterPilotPlayable/KnightPaletteSafeVAT.asset`；其Full子资产来自同目录中间profile，不能误删依赖。新增Scenario和稳定Catalog缺一不可。
- 仍有密集接触网格溢出/现役搜敌上限提示，列为后续调校，不伪装成零警告；Far为强制GPU验证，人工观感/自然镜头切换待签收。
- 本例固定分阶段配方、输出防覆盖；再次制作需新路径/版本。完整入口、许可、实测与边界见[试点报告](../../Docs/CharacterPilot-20260930/README.md)。
