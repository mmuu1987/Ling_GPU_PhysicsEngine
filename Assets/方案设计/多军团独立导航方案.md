# 多军团独立导航方案

> 状态：**方案，未实现**。写于 2026-09-05，对应 `ROADMAP.md` 阶段 2。
> 这是唯一值得动引擎数据契约的功能需求，所以下面的量化写得比平时细。

## 目标与非目标

**目标**：让 N 支军团各自拥有独立的流场导航与敌对判定，而不是现在的「攻方一张场 + 守方一张场」。
玩法上要能做到：三方混战、一方分成两路包夹、某支军团单独换目标而其他军团不受影响。

**非目标**（这一轮明确不做）：

- **结盟**。下面的方案里「不同军团」等价于「敌对」。同盟需要额外的关系表，见末尾「如果将来要结盟」
- 三维导航（另有 `流场三维扩展方案.md`）
- 每军团独立的流场分辨率/原点。所有军团共享一套网格参数，这是简化的关键前提

## 现状：硬编码的 2 在哪

引擎现在不是「支持 2 队的通用实现」，而是**attacker 一套 + defender 一套的平行复制**。
精确位置（行号对应 `a5f14b3`）：

| 位置 | 现状 | 性质 |
|---|---|---|
| `AgentDataCommon.hlsl:1012` `IsEnemy` | `teamIdReadBuffer[self] != teamIdReadBuffer[other]` | **已通用**，N 队天然成立 |
| `AgentSpatialHash.compute:77` | `if (teamId < 0 \|\| teamId > 1) return;` | 硬边界的实际位置 |
| `AgentSpatialHash.compute:44` | `teamSlot = (team == defenderTeamId) ? 1u : 0u` | 二值分桶 |
| `AgentSpatialHash.compute:83` | `baseIndex = teamId * 8`（`teamSpatialStats` 16 int） | 遥测按 2 队定长 |
| `AgentDataCommon.hlsl:586/602` | `SampleFlowDirection` / `SampleDefenderFlowDirection` 两个函数 | 平行复制 |
| `AgentCombatSimulation.compute:86/354/376` | `IsDefenderTeam(...) ? SampleDefender... : Sample...` | 二选一分支，**只有 4 处调用** |
| `AgentDataCommon.hlsl:652` `SampleFriendlyDensityCell` | `team == attackerTeamId ? attackerDensityMap : defenderDensityMap` | 二选一分支 |
| `AgentRuntimeFlow.compute` | 8 个 kernel：`*Attacker*` 4 个 + `*Defender*` 4 个，逻辑逐行平行 | 平行复制 |
| `MassGpuBufferManager.cs:133-140` | 6 个成对 buffer（directions / targetDensity / stats / targets） | 平行复制 |
| `RuntimeFlowConfig.cs` | 字段成对：`dynamicFlow*` / `dynamicDefenderFlow*` | 平行复制 |

**结论**：真正需要设计的是「把平行复制折叠成按索引寻址」，敌友判定几乎不用动。
`teamIdReadBuffer` 已经是队伍身份的唯一来源（`AgentDataCommon.hlsl:5` 的注释明确写了这条），
没有任何 kernel 按索引区间推断阵营 —— 这是这次改动能收敛的根本原因。

## 核心决策 1：放宽 `teamId` 取值域，不引入第二个身份维度

**「军团」= 一个 team。** `teamId` 从 `{0, 1}` 放宽到 `{0 .. groupCount-1}`，不新增 `groupId` 字段。

理由：新增 `groupId` 意味着敌对判定要从「team 不同」变成「查 group 关系表」，
`IsEnemy` 从一次 buffer 读变成两次读 + 一次表查，而它在寻敌内循环里被调用的次数是
`agent × 邻域候选` 量级 —— 这是全引擎最热的谓词之一。
放宽取值域则 `IsEnemy` 一行都不用改。

代价：**不支持结盟**。这是明确接受的取舍，理由见末尾。

需要跟着改的是「attacker/defender 这两个具名概念」：

- `attackerTeamId` / `defenderTeamId` 两个 uniform 现在承担两件事 —— ①选流场 ②选守方行为分支
  （`IsDefenderTeam` 决定用 aggro 半径还是 `attackRange`）
- ①由「按 `teamId` 索引流场」取代，uniform 可以删
- ②不是队伍属性而是**战术姿态**（推进 / 固守）。应该从 `teamId` 判断改成 per-group 的
  `stanceIsHold` 标志（一个 `int[groupCount]` buffer 或打包进流场参数 buffer）。
  这样「两支军团都固守」「三方都推进」才表达得出来

## 核心决策 2：buffer 按 group 分段，不是每 group 一个 buffer

寻址一律 `group * cellCount + cell`。项目里已有这个模式 ——
`AgentSpatialHash.compute:45` 的 `teamCellIndex = teamSlot * gridCellCount + cellIndex`，
照抄即可，不是新发明。

好处：buffer 数量不随军团数增长（Unity 的 `ComputeBuffer` 绑定槽位有限，
16 支军团 × 6 个 buffer = 96 个绑定是不可行的）；kernel 数量也不增长 ——
8 个成对 kernel 折叠成 4 个，`groupCount` 进 dispatch 的 z 维或作为 uniform 循环。

## 显存代价（实配 720×720 世界 / cellSize 3 / maxAgentsPerCell 18 / 流场 256²）

| 缓冲 | 单 group 大小 | 随 group 增长 |
|---|---:|---|
| `teamGridAgentIndices` 57600 格 × 18 槽 × 4B | **3.96 MiB** | 是 |
| `teamGridCounts` 57600 × 4B | 225 KiB | 是 |
| `flowFieldDirections` 65536 × 8B | 512 KiB | 是 |
| `targetDensity` 65536 × 4B | 256 KiB | 是 |
| `densityMap` RT 256² ARGB32 | 256 KiB | 是 |
| flow preview RT（可关） | 256 KiB | 是 |
| `flowStats` 4 int + `flowTargets` 8 × float4 | 144 B | 是 |
| `gridAgentIndices`（全局，不分队） | 3.96 MiB | 否 |

**每军团约 5.4 MiB。** 2 支 = 10.8 MiB（现状），8 支 = 43 MiB，16 支 = 87 MiB。

结论：**显存不是障碍**，16 支军团以内都在现代 GPU 的零头里。
真正的成本是下面的每帧开销。注意 `MassGpuBufferManager.cs:123-128` 已有的溢出保护
（`teamGridIndexCapacity > int.MaxValue / 4` 就拒绝分配并报错）要把 `* 2L` 换成 `* groupCount`，
否则 16 支军团 × 大世界会静默溢出成负数 stride。

## 每帧开销：这才是真正的上限

- **流场重建**：`Build density → Select targets → Generate` 三个 kernel，现在攻方每
  `dynamicFlowUpdateInterval`（默认 0.35s）跑一轮。N 军团 = N 轮。Generate 是
  `65536 / 64 = 1024` 个线程组，密度构建是 `agentCount / 64`。
  按 group 分段后可以**一次 dispatch 覆盖所有 group**（线程数 × groupCount），
  比 N 次 dispatch 省掉 N-1 次 launch 开销，但总带宽照样是 N 倍
- **重建节流要错峰**：N 支军团若共用一个计时器会在同一帧一起重建，做出一个 N 倍尖刺。
  应给每个 group 一个相位偏移（`interval * group / groupCount`），把尖刺摊平成每帧一支
- **spatial hash 分桶**：`BuildSpatialHash` 里每个 agent 写一次自己的 group 桶，
  开销与 group 数无关（O(agent)），只有 clear 是 O(groupCount × cellCount)
- **寻敌**：`IsEnemy` 现在读**所有非我 group 的桶**，而不是「唯一的敌方桶」。
  这是唯一一处复杂度真的从 O(1) 变 O(N) 的地方 —— 邻域查询要遍历 N-1 个桶。
  8 支军团时寻敌邻域读取量约 7 倍。**这是方案里最需要实测的一项**，
  缓解手段是先按距离剔除 group（用已有的 `teamSpatialStats` 里的 group 包围盒，
  离得远的 group 整体跳过），但先按朴素实现测出真实数字再决定要不要做

## 改动清单（可增量落地，每步都能单独跑测试）

**第 1 步 —— 把 2 参数化成 `groupCount`，行为不变。**
`groupCount = 2` 时结果必须与改前逐帧一致（这是这一步的验收标准）：

- `MassGpuBufferManager.Allocate` 签名加 `groupCount`，`* 2L` / `* 2` 全部换成它
- `teamSpatialStats` 从 16 int 变 `groupCount * 8`
- `AgentSpatialHash.compute:77` 的 `teamId > 1` 换成 `teamId >= groupCount`
- `AgentSpatialHash.compute:44` 的三元换成 `uint teamSlot = (uint)teamId`

**第 2 步 —— 流场折叠。**8 个 kernel → 4 个，6 个成对 buffer → 3 个分段 buffer：

- `flowFieldDirections` 与 `defenderFlowFieldDirections` 合并为
  `float2[groupCount * cellCount]`；`targetDensity` / `flowStats` / `flowTargets` 同理
- `SampleFlowDirection` / `SampleDefenderFlowDirection` 合并成一个按 `teamId` 寻址的版本，
  4 处调用点的二选一分支消失（`AgentCombatSimulation.compute:86/354/376`）
- `RuntimeFlowConfig` 的成对字段合并成单份 + per-group override 列表；
  `defenderFlowFieldEnabled` 变成 per-group 开关（**注意现在它是 `0`，守方流场默认关闭**，
  合并后要保持守方仍然不受流场牵引，否则默认场景行为会变）
- `attackerDensityMap` / `defenderDensityMap` 同样合并，`SampleFriendlyDensityCell` 去分支

**第 3 步 —— 姿态与阵营配置。**把 `attackerTeamId` / `defenderTeamId` 两个 uniform 删掉，
换成 per-group 的 `stanceIsHold`；`IsDefenderTeam` 改名成 `IsHoldStance`，语义从「是守方」
变成「这支军团在固守」。`enableTwoTeamCombat` 改成 `groupCount > 1`。

**第 4 步 —— 游戏层。**`WarSandboxBattleController` / `ArmyOrder` / HUD 从「攻守两方」
扩到 N 军团：出生编队、下令目标、遥测面板（`BattleTelemetry` 现在也是 2 队定长）。
这一步纯游戏层，不动引擎契约，可以和第 1-3 步并行设计。

**第 5 步 —— `UnitTypeGpuSettings`。** 若 per-unit-type 需要新 GPU 字段（例如默认姿态），
复用现存的 `padding0`-`padding6` 坑位改名即可，stride 与 144 字节不变；
**在末尾追加字段会撑破 144，导致 `MassGpuBufferManager.cs:101` 运行时拒绝分配整个 buffer**。

## 风险与验证

| 风险 | 缓解 |
|---|---|
| 第 1 步引入静默行为漂移 | 验收标准就是 `groupCount = 2` 时逐帧一致；先跑现有 PlayMode 29 项，再加一项两队场景的确定性对比 |
| 寻敌开销 O(N) 失控 | 第 2 步做完先在 4 群 × 12500 的场景实测帧时间，再决定要不要做 group 包围盒剔除 |
| 流场重建同帧尖刺 | 相位错峰（见上），并在 HUD 上暴露「本帧重建了哪几支军团」 |
| 默认场景行为变化 | 守方流场当前 `defenderFlowFieldEnabled: 0`，合并后必须保持关闭 |
| 大世界 × 多军团 buffer 溢出 | `MassGpuBufferManager.cs:123` 的容量检查按 `groupCount` 缩放，报错信息里给出建议的 `groupCount` 上限 |

新增测试（按项目既有风格放 `Assets/MassEngine/Tests/PlayMode/`）：

- `ThreeGroupsEachFollowOwnFlowField`：三支军团三个不同目标点，断言各自朝各自方向
- `GroupCountTwoMatchesLegacyTwoTeamBehaviour`：第 1 步的回归闸门
- `EveryNonSelfGroupIsHostile`：三支军团互相都能选到目标，不会只打其中一支

## 如果将来要结盟

在 `teamId` 之外加 `allianceId`，`IsEnemy` 改成
`allianceIdReadBuffer[self] != allianceIdReadBuffer[other]`（仍是一次比较，不是关系表），
流场与分桶继续按 `teamId`（军团）走。这样「同盟不同军团、各走各的路」就成立了，
而热路径谓词的代价不变。**只有真的需要结盟玩法时才做**，因为它给每个 agent
多一份身份 buffer，也让「谁是敌人」多一层间接。
