# 流场三维扩展方案

## 结论

当前项目不建议把主导航系统直接从 XZ 平面流场升级成完整 XYZ 体素流场。更合适的路线是做“表面 3D 化”：

- 视觉和最终位置可以是 3D。
- 主导航拓扑尽量保持 2D 或分层 2D。
- 只有飞行、水下、技能力场等少数系统单独使用局部或稀疏 3D。

这个方向更接近大规模战争模拟的取舍：牺牲一部分通用精确寻路，换取海量单位、稳定性能和可控实现成本。

## 参考方向

以 Ultimate Epic Battle Simulator 2 这类大规模战争模拟为参考，公开资料能确认的是它强调百万级单位、GPU 驱动的群体渲染和个体 AI，但没有公开完整寻路算法。因此这里不能断言它内部一定用了某种具体流场算法，只能把它作为设计方向参考：

- 大规模单位系统通常不会让每个普通地面单位跑完整 3D 导航。
- 更可能采用宏观目标吸引、局部避让、密度压力、简单群体规则和 GPU 批量模拟。
- 对普通步兵来说，“贴地表面的 3D 表现”比“完整体积空间寻路”更划算。

## 当前系统判断

Stage7 当前流场体系是完整的 XZ 平面设计：

- `flowFieldDirections` 是 `float2`。
- `flowFieldOrigin` 是 `Vector2`。
- agent 位置读写 buffer 使用 XZ 的 `float2`。
- shader 中大量逻辑使用 `position.xz`。
- `ClampVelocity` 中会把 `velocity.y` 强制归零。
- 密度图、动态 attacker/defender flow、局部避让、预览贴图都围绕二维网格设计。

所以完整 XYZ 不是简单把 `float2` 改成 `float3`，而是会牵动 buffer、shader、密度、碰撞、边界、预览和编辑工具。

## 推荐路线一：地形表面投影流场

这是最推荐的第一步。

保留 XZ 流场，让流场继续输出水平意图方向；同时增加地形高度和法线采样。单位根据 XZ 坐标采样地面高度，更新 `position.y`，并把水平流场方向投影到地形切面上。

概念公式：

```hlsl
float3 horizontal = float3(flow.x, 0, flow.y);
float3 tangentDir = normalize(horizontal - normal * dot(horizontal, normal));
```

这样单位实际移动方向是 3D，可以上坡、下坡、贴合地形，但流场内存和密度系统仍然保持二维。

适合场景：

- 普通地面战场。
- 有高低起伏的地形。
- 坡地、丘陵、山谷。
- 角色需要视觉上贴地运动。

优点：

- 改动面最可控。
- 性能接近当前二维流场。
- 与现有 GPU 群体逻辑兼容。
- 能解决大多数“从平面扩展到三维表现”的需求。

## 推荐路线二：多层 XZ 流场 + Portal

如果后续要支持桥、城墙、楼梯、多楼层平台，不建议直接上完整 3D voxel。更好的方式是把每个可行走表面当成一层 2D flow field。

设计方式：

- 每层有自己的 XZ flow field。
- 楼梯、坡道、门洞、桥头作为 portal。
- CPU 或预处理阶段决定“从当前层去目标层应该走哪个 portal”。
- GPU 单位在当前层继续采样二维流场。
- 进入 portal 区域后切换层。

适合场景：

- 城墙和城门。
- 高架桥。
- 楼梯和平台。
- 地下层、地面层、屋顶层。

优点：

- 比完整 3D 流场便宜很多。
- 能表达多层拓扑。
- 保持当前 XZ 密度、避让、流场预览的大部分结构。

## 推荐路线三：目标吸引 + 局部群体行为

对于模拟战争类大规模开放战场，很多时候不需要全局寻路特别精确。流场可以只是宏观趋势，真正的队形和绕堵靠局部行为。

可以强化这些行为：

- 目标点或敌人吸引力。
- separation 局部分离。
- density pressure 密度压力。
- lane bias 稳定侧向偏移。
- 阵营或小队方向。
- 边界和障碍排斥。

这条路线和当前 Stage7 已有的动态 attacker/defender flow、density pressure、separation 是兼容的。后续可以继续把流场当成“战略方向”，而不是要求它解决所有寻路问题。

## 推荐路线四：稀疏 3D 或局部 3D 力场

完整 XYZ 体素流场只建议给特殊系统，不建议作为普通地面单位的主导航。

适合使用局部 3D 的场景：

- 飞行单位。
- 水下或太空单位。
- 被技能卷起、击飞、吸入黑洞的单位。
- 局部洞穴或空中战斗区域。

实现方向：

- 使用 sparse voxel 或 brick grid。
- 只在需要的局部区域分配 3D 数据。
- 普通地面单位仍走表面流场。
- 技能力场可以直接对速度施加 3D force，不必生成全局 3D flow field。

## 不推荐路线：全局 XYZ 体素流场

直接把整个战场改成 `x * y * z` 的全局体素流场风险很高。

主要问题：

- 内存暴涨。`128^3` 已经是 2,097,152 个 cell，方向 `float3` 约 24 MB；如果再加攻击方、防守方、密度、目标、预览和临时 buffer，成本会继续上涨。
- shader 改动范围大。流场采样、密度、分离、边界、目标统计和动态生成都要三维化。
- 编辑工具复杂。手绘三维流场比二维困难很多，调试和预览也更麻烦。
- 对普通地面军团收益不高。大多数单位仍然只需要沿地表移动。

## 后续执行顺序

建议未来做到这块时按以下顺序推进：

1. 先做地形高度和法线采样，让单位能贴地移动。
2. 把最终速度从纯 XZ 改成沿地形切面的 3D 速度。
3. 保留二维流场、二维密度和二维局部避让作为主路径。
4. 如果出现桥、城墙、楼层，再加多层 XZ flow field 和 portal。
5. 如果出现飞行、水下、黑洞技能，再为这些系统单独做局部 3D 力场或稀疏 3D。
6. 只有当核心玩法明确依赖完整体积空间寻路时，再评估全局或分块 XYZ flow field。

## 最终原则

主导航不要急着追求数学意义上的完整 3D。这个项目更需要的是：

- 大规模单位稳定运行。
- 视觉上支持三维地形。
- 普通地面单位使用便宜、稳定、可调试的表面导航。
- 特殊单位和特殊技能再局部引入 3D。

因此未来实现时，以“2D 流场 + 地形高度/法线 + 多层 portal + 局部 GPU 群体行为”为主线。
