# 场景规则归档方案

> 状态：M3 预研，未实现。2026-09-06。
> 产品目标：[GAME_DESIGN.md](../../GAME_DESIGN.md) 的 M3；实施必须另起分支，不并入本轮 M2 代码。

## 1. 结论与代码现状

先增加游戏层的战场规则定义资产，复用现有 Controller 和 War Sandbox Editor。
M3.1 只归档规则与障碍，M3.2 再加战场目录与运行时入口，不一次实现玩家存档系统。

现有依据：

- `WarSandboxBattleController` 拥有模式、控制点和障碍字段；控制点捕获状态、军团命令是运行时状态。
- `ScenarioConfig` 仅保存兵种列表；空间尺寸由 Simulation/RuntimeFlow 配置承担。
- `WarSandboxDeploymentPlan` 属于 `Game.Editor`，依赖 UnityEditor，且载入会修改项目资产。
  `Game` 不能引用它；它也没有保存源 Scenario 的身份，不能假设已有方案与某 Scenario 的身份校验。
- `WarSandboxRuntimeBootstrap` 在场景加载后补 Controller/HUD；部分旧场景没有显式 Controller。
- `StaticObstacleMath.MaxObstacleCount` 当前为 8；不扩大 GPU 障碍契约。

因此运行时规则资产不持有 `WarSandboxDeploymentPlan`，也不在加载时调用其 `TryApply`。
M3 的默认部署就是场景已配置的 Scenario/Spawn；玩家运行时布阵与存档留给 M4。

## 2. M3.1：规则资产与制作入口

建议类型名 `WarSandboxBattlefieldConfig`，放入 `Game` 程序集，名称在实施时可按现有习惯调整。

```text
WarSandboxBattlefieldConfig (Game)
  gameMode
  controlPointCenter
  controlPointRadius
  controlPointCaptureSeconds
  obstaclesEnabled
  obstacleClearance
  obstacles[]             // 显式布局，最多 8 个 XZ 矩形
```

不加入胜者、占领进度、命令、SceneAsset、UnityEditor 类型或引擎 buffer 参数。
暂不另开一套编辑器：在当前 War Sandbox Editor 中增加选择、另存、载入规则定义和校验入口。
单位部署和规则是两个明确的资产对象，不让保存其中一个悄悄改写另一个。

### 应用边界

- 绑定定义时复制规则和障碍数组到 Controller 的本局状态；只读共享定义。
- 显式应用仅允许 Setup；先完整校验，再一次替换，不先改模式再发现障碍非法。
- 每帧逻辑使用本局值，不每帧覆盖玩家在 Setup 中的模式选择。
- 重开恢复当前已选择定义的初始规则；定义没绑定的旧场景保持原有组件默认值和行为。
- 保存内置障碍布局时保存实际解析结果，不能把未启用的自定义数组当成当前地图。
- 编辑器操作支持一次 Undo；配置字段写入仍禁止 Unity Play Mode。
- 若旧场景没有 Controller，通过明确的编辑器动作创建/绑定并支持 Undo，不能只依赖运行时补组件来制作资产。

### 校验

模式必须合法；数值有限。据点半径与捕获时长沿用 Controller 的现有最小值，clearance 非负。
障碍数量不超过上限，矩形满足 `IsValid`；禁用障碍不清空已制作布局。
定义中的无效数据应报告具体字段，不静默截断地图或部分应用。
默认预设还需要检查据点、出生区域和障碍的可玩关系，不能仅通过类型校验就算可玩。

### M3.1 验收

在同一场景中制作规则 A（歼灭、无障碍）和 B（据点、自定义障碍），交替载入并进入 Play。
模式、半径、占领时间、障碍和重开都与选中定义一致；退出 Play 后两份定义未被污染。
未绑定规则的既有场景仍按旧方式开战，编排和部署方案的验收功能不回退。

## 3. M3.2：目录与入口

再增加显式的战场目录条目，包含稳定 ID、显示名、构建场景路径和规则定义引用。
不在运行时扫描 AssetDatabase、文件 GUID 或按场景名前缀猜资源。
Editor 侧可提供 SceneAsset 选择便利，构建数据只保留经验证的场景路径。

首版可复用现有 `WarSandbox` 与 `WarSandboxSample` 场景作内容起点，但它们当前不因此自动算作两个已交付战场。
每个条目的默认部署来自该场景 Manager 的既有只读配置。
调整其中一个预设时，共享部署资产需要制作期显式复制；规则资产隔离不会自动解决共享 Spawn 的编辑污染。

```text
游戏内选择条目
  -> 验证条目、规则引用和可加载场景
  -> 带加载状态进入场景
  -> 显式传递选定规则给 Controller，保持 Setup
  -> 验证 Manager 默认配置和规则均就绪
  -> 允许玩家开战
```

具体接线在 M3.2 根据 Manager 初始化顺序实现，必须保证新入口在定义就绪之前不先派发战斗。
不能假设现有 AfterSceneLoad bootstrap 可以在 GPU 初始化之前替换 Scenario。
M3 不需要运行时替换部署资产；若 M4 要修改部署，另设初始化/释放边界并补生命周期测试。

选择请求显式传递到新场景，使用后清除；下一次直接进入场景不携带上一个条目。
加载前失败保持当前页面；加载后失败禁用开战并可返回入口，不宣称能恢复已经卸载的上一局。
返回入口清除旧 Controller、障碍呈现、命令和速度，释放旧场景 GPU 资源；不叠加两个模拟场景。
交战中换场需先确认结束本局，不能无提示覆盖当前战局。

## 4. 测试与实施顺序

### M3.1 的提交

1. 游戏层定义类型和纯校验；测试合法默认值、非法模式/数值/矩形和障碍上限。
2. Controller 的绑定与应用；测试 A/B 切换、数组独立性、失败不修改状态、重开、旧场景兼容。
3. 现有编辑器中的保存/载入与 Undo；测试磁盘往返和 Play Mode 写保护。
4. 实际场景烟测，并由用户验收模式、障碍、据点变化。

### M3.2～M3.3 的提交

1. 目录与场景绑定校验，包括重复 ID、缺失规则和未纳入构建的场景。
2. 运行时入口、错误返回、两份可玩默认内容，保持项目配置只读。
3. PlayMode 场景切换/重开烟测，以及真实 Windows 构建检查，排除 Editor-only 引用。
4. 依次进入 A、B，分别开战结算并重开；检查选中军团、规则、障碍、速度和结算没有跨局残留。

不在本阶段增加地图绘制、动态障碍、联盟、三维流场、账号或资源热更新。
交付门槛是两个战场可从成品入口往返运行，不是新建两个配置文件就算完成。
